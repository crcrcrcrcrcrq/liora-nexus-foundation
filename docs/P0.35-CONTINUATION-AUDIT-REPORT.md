## 1. Executive Summary

This stage was a continuation audit, not a rebuild. The current source tree from
`tele-insight-stream-main.zip` was installed as the live project unchanged
(no historical snapshot was merged), then audited statically and at runtime.

Architecture, routing, locale isolation, CMS, Theme Manager, Blog, Services,
Booking, Schedule, Notifications, Telegram Admin, Telegram Statistics,
Analytics and Admin authorization were reviewed and found consistent with the
decisions recorded in the history archive. No module was rewritten and no
parallel system was introduced.

Three real defects were found and fixed (all P1):

1. `sitemap.xml` emitted **relative** `<loc>` and `hreflang` URLs — invalid per
   the Sitemap protocol; search engines reject such entries.
2. `robots.txt` was a static file with **no `Sitemap:` directive** and did not
   disallow the private Sanctuary area, which without a session renders only an
   access/loading state (thin, indexable page).
3. `createBooking` accepted **any non-empty string as an e-mail** and had no
   length/format limits on `name`, `message`, `preferredDate`, `preferredTime`,
   `serviceSlug` — client-trusted values on a public write path.

Public runtime (28 PL/EN routes at 390×844), build, typecheck and lint are GREEN.
Backend-dependent surfaces (staff session, database rows, e-mail transport,
Telegram handshake) are **NOT VERIFIED** — no backend is provisioned in this
environment and nothing was fabricated.

**FINAL STATUS: AMBER** — code GREEN, public runtime GREEN, backend/integration
runtime blocked by environment.

## 6. Findings

### 6.1 P0 — production/security blockers

**None found in the current source.** Specifically checked and clean:

- No role accepted from a client payload; `requireStaffRole` reads `user_roles`
  server-side on every admin call and on every Telegram Admin command.
- Telegram webhooks verify `X-Telegram-Bot-Api-Secret-Token` with
  `timingSafeEqual` before doing anything, per bot, with separate secrets and
  separate allowlists.
- Telegram allowlist grants no authority by itself — the DB role is re-checked
  per command, so revoking a role in the database immediately cuts the bot off.
- `supabaseAdmin` is only imported dynamically inside server-only modules; no
  service-role key path reaches the client bundle.
- `createBooking` sets `user_id` from the SSR session, never from the payload;
  ownership is enforced by RLS and a unique index guards the race.
- Booking status transitions are re-validated server-side (`canTransition`),
  the UI only renders allowed transitions.
- Notification idempotency: cancellation uses `neq('status','cancelled')` so a
  repeated call updates no row and dispatches no second event; dispatch failure
  never rolls back or changes the client response.
- Analytics contains no IP column, no fingerprinting, no UA parsing; location
  comes only from runtime headers; `metadata` is reduced to a 4-key allowlist;
  `path` is stripped of query and fragment.

### 6.2 P1 — important production issues (all FIXED this stage)

| ID | Finding | Evidence | Fix |
|----|---------|----------|-----|
| P1-1 | `sitemap.xml` emitted relative `<loc>`/`hreflang` (`/pl`, `/en/...`). The Sitemap protocol requires absolute URLs; the file was effectively unusable. | RUNTIME: `curl /sitemap.xml` returned `<loc>/pl</loc>`. | New `src/lib/site-url.server.ts` resolves an absolute base from `VITE_SITE_URL`, falling back to the request host. Sitemap now emits absolute URLs. |
| P1-2 | `public/robots.txt` was static: no `Sitemap:` directive (it requires an absolute URL, impossible in a static file) and no `Disallow` for the private Sanctuary area. | RUNTIME: `curl /robots.txt`. | Replaced with server route `src/routes/robots[.]txt.ts`; same rules plus `/sanktuarium`, `/pl/sanktuarium`, `/en/sanctuary`, plus an absolute `Sitemap:` line. Static file deleted so the route is authoritative. |
| P1-3 | `createBooking` validated only "non-empty string": any text passed as e-mail; `name`/`message` unbounded; `preferredDate`/`preferredTime`/`serviceSlug` unconstrained in format. Public write path. | CODE: `parseBookingInput` in `src/lib/booking.functions.ts`. | Server-side format and length enforcement: e-mail pattern + 254 chars, name ≤ 120, message ≤ 2000, `YYYY-MM-DD`, `HH:MM`, slug pattern. Business rules (service/schedule/slot) unchanged. |

### 6.3 P2 — polish / technical debt (documented, NOT changed)

- `getAvailability` parses `serviceSlug` in its `inputValidator` but the handler
  ignores it. Harmless dead input; changing the contract was out of scope.
- 39 ESLint `react-refresh/only-export-components` warnings in `src/pages/*`
  (each page exports both `page` and a component). This is the intentional
  `definePage` pattern; warnings only, no errors.
- Canonical `<link>` remains relative when `VITE_SITE_URL` is unset. Legal and
  correctly resolved by browsers and crawlers, but absolute canonicals are
  preferable once the production domain is configured.
- `docs/` contains reports for P0.3.1, P0.32, P0.34 only; earlier stages live in
  the history archive rather than the repository.

### 8.12 Analytics / GDPR verification — GREEN (CODE) / partial RUNTIME
- No IP column anywhere in the analytics model or insert path. CONFIRMED.
- No fingerprinting: device type is derived from viewport width; no UA parsing,
  no canvas/font probing. CONFIRMED.
- Visitor key: `crypto`-random, pseudonymous, rotated every 30 days. CONFIRMED.
- Location limited to country/region/city from runtime headers. CONFIRMED.
- `metadata` reduced to the allowlist `surface|variant|spread|service`, each
  value ≤ 48 chars; anything else is dropped by the Zod transform. CONFIRMED.
- `visitor_type` and referrer category are decided server-side; the client
  cannot forge them. CONFIRMED.
- Ingestion writes with the service key because the table has no public INSERT
  policy. CONFIRMED as intended design.
- Persisting the event rows themselves was **not** exercised (no database).

**Open GDPR item (not a defect introduced here, not fixed here):** analytics
starts without an explicit consent gate, and the pseudonymous key is stored in
`localStorage`. For a PL/EU audience this is a product/legal decision (some
regimes accept strictly-necessary pseudonymous measurement, others require prior
consent). Raised as a **P1 for the next stage** rather than silently adding a
consent-banner subsystem, which would be a new system and outside this stage's
mandate.

   Telegram cannot be exercised here.

   warnings; harmless by design.
