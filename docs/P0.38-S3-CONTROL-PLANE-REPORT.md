Telegram Admin and Telegram Statistics call the same business functions and the
same role checks. Neither has its own permission store.

## 4. S3 Architecture

Target endpoint `https://s3.ipswarm.com`, region `garage`, bucket `ip-36234`,
**path-style** addressing. Endpoint/bucket/credentials are read from server
environment only; the values are not in the repository, not in the client
bundle, not in Telegram, not in this ZIP.

```text
liora/
├── backups/<releaseId>/manifest.json + <artifact>
├── releases/<releaseId>/release.json
├── deployments/<releaseId>/...        (reserved for the deployment engine)
├── checkpoints/<releaseId>/<checkpointId>.json
├── artifacts/
└── logs/
```

Release id format: `LIORA-2026.08.10-001` (`LIORA-YYYY.MM.DD-NNN`), validated by
`RELEASE_ID_PATTERN` and unit-tested.

## 5. Storage Adapter

- `src/lib/storage/model.ts` — client-safe types, `StorageError` with codes
  (`not_configured`, `invalid_key`, `not_found`, `access_denied`, `upstream`,
  `network`), key builders with a strict segment allowlist (rejects `..`, `/`,
  empty), release id helpers, forbidden-artifact allowlist.
- `src/lib/storage/s3.server.ts` — server-only. `putObject`, `putJsonObject`,
  `getObject`, `getObjectText`, `getJsonObject`, `deleteObject`,
  `objectExists`, `listObjects`, `checksum`, `readStorageConfigStatus`.
  SigV4 is computed in-process with Web Crypto (`crypto.subtle`), so it works in
  the Workers runtime; no AWS SDK, no Node-only dependency was added.
  `process.env` is read inside functions only. Credentials are never logged,
  never returned, never serialised; `fetch` rejections are re-thrown as
  `StorageError("network", …)` so a signed URL can never leak through an error.

## 6. Backup Manager

`src/lib/backups/model.ts` (pure) + `src/lib/backups/manager.server.ts`.
Manifest fields: `backupId`, `releaseId`, `createdAt`, `projectVersion`,
`gitCommit | null`, `checksum` (`sha256:…`), `sizeBytes`, `artifactKey`,
`status` (`draft | uploading | stored | failed`), optional short `note`.
Operations: create manifest, upload artifact (computes checksum, updates
manifest, marks `failed` on error), list backups, get metadata.
`assertSafeArtifactName` refuses `.env*`, `*.pem`, `*.key`, `id_rsa`,
`*credentials*`, `*secret*`. No customer data is part of a system backup.

## 7. Release Manager

`src/lib/releases/model.ts` + `manager.server.ts`. Statuses:
`draft | building | ready | deployed | failed | rolled_back`, with an explicit
transition table — `draft → deployed` is impossible, and no-op transitions
(`ready → ready`) are rejected with `RELEASE_STATUS_TRANSITION_INVALID`.
`nextReleaseId()` derives the next free daily sequence from S3 without writing.
No fabricated success status exists.

## 8. Checkpoint Manager

`src/lib/deployment/model.ts` + `checkpoints.server.ts`. The ten checkpoints
(`01-init … 10-production`) are declared as a closed union and start `pending`.
Each record carries id, releaseId, status, timestamp, summary, errors, metadata.
`sanitizeCheckpointMetadata` drops any key matching secret/token/key/credential/
cookie/ip/email/phone/user_agent and any value that looks like an e-mail or an
IPv4 address. **No automatic rollback is implemented in P0.38** — only the
`rolled_back` release status exists as the future hook.

## 9. Control API Foundation

`src/lib/control/model.ts` declares the eight modules (`auth`, `roles`,
`deployment`, `backups`, `releases`, `storage`, `checkpoints`, `health`) and the
permission set (`control:read`, `control:storage:read`, `control:backup:write`,
`control:release:write`, `control:deployment:write`). `admin` gets all,
`moderator` read-only.

`src/lib/control/authorize.server.ts` does not introduce a second permission
system: it delegates to the existing `requireStaffRole` (panel session) and the
existing `resolveStaffIdentity` (Telegram allowlist + live `user_roles` check).
The allowlist only *maps* a Telegram ID to a LIORA user; the database remains
the authority, so revoking a role in the DB instantly removes Control Plane
access without touching configuration.

`src/lib/control.functions.ts` exposes exactly one read operation
(`fetchControlPlaneStatus`) behind the session middleware. No write operation is
exposed to any client in P0.38.

## 10. Telegram Integration Boundary

Both existing channels are untouched (`src/lib/telegram-admin`,
`src/lib/telegram-stats`, both webhook routes, both allowlists). No third bot.
The future Mini App is expected to call the Control API; identity resolution is
already the single chain `Telegram User → Telegram ID → LIORA User → LIORA Role
→ Permission`. Telegram cannot grant itself a role: there is no code path from a
Telegram update to `user_roles` writes.

## 17. Limitations

- No deployment engine, no rollback execution, no Mini App, no deployment GUI.
- The Control Plane exposes read-only status; every write operation is still
  server-side-only and not wired to any client.
- Backup artifacts must be produced outside the Worker runtime (no
  `child_process` there); the manager stores and describes them, it does not
  create archives itself.
- `listObjects` parses S3 XML with targeted regexes (no XML dependency added);
  it is sufficient for ListObjectsV2 `Contents` entries.
