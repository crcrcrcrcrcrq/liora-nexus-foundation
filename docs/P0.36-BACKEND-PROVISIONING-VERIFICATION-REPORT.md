## 1. What was done

### 1.1 Backend provisioning

Lovable Cloud was enabled for the project. No new architecture was invented: the
schema was reconstructed **exclusively from the 28 migration files already in
`supabase/migrations/`**.

Analysis of those 28 files showed they are not a linear chain — several are
**cumulative snapshots** that re-create everything from `app_role` downwards
(`20260807231606`, `20260808003439`, `20260808031317`, `20260808041954`,
`20260808044335`, `20260808203927`, `20260809022238`). Replaying them verbatim
in filename order on a fresh database fails at the second snapshot
(`type "app_role" already exists`).

The final snapshot, `20260809044150_d04b6d58…sql`, is fully idempotent
(`DO $do$ … EXCEPTION WHEN duplicate_object`, `CREATE TABLE IF NOT EXISTS`,
`DROP POLICY IF EXISTS`, `ADD COLUMN IF NOT EXISTS`) and is the authoritative
consolidated baseline of the whole lineage. Applied schema, in order:

1. `20260807220709` — identity foundation (verbatim).
2. `20260807220724` + `20260807220842` — least-privilege revokes/grants (verbatim).
3. `20260809044150` — consolidated baseline, verbatim (all tables, policies,
   functions, triggers, seed data).
4. `20260809111101` — `analytics_events`, verbatim.
5. **New, P0.36:** `REVOKE ALL ON public.analytics_events FROM anon` (see §3.1).

No SQL was rewritten, re-authored or "improved"; the intermediate snapshots are
subsets of the consolidated baseline and are preserved on disk untouched.

### 1.2 Resulting schema — verified against the live database

12 tables in `public`: `analytics_events`, `blog_posts`, `booking_schedule`,
`bookings`, `chronicle_notes`, `chronicle_reflections`, `chronicle_rituals`,
`profiles`, `services`, `site_content`, `site_settings`, `user_roles`.

Seed data present as defined by the migrations: **5 services**, **5 schedule
windows** (Mon–Fri 10:00–18:00), 1 `site_settings` row.

Functions: `has_role`, `set_updated_at`, `handle_new_user`, `booked_dates`,
`active_schedule_weekdays`, `active_schedule_windows`,
`bookings_validate_language`. Triggers including `on_auth_user_created` and the
unique index `bookings_one_active_per_date` are in place.

## 3. Defects found and fixed in P0.36

### 3.1 P1 — `analytics_events` readable by the anonymous role (privilege, not data)

The original migration granted SELECT only to `authenticated`, but Cloud's
default grant on new public tables left `anon` holding SELECT. RLS still
returned zero rows (no `anon` policy), so **no analytics data was ever
exposed** — but the privilege contradicted the project's least-privilege
posture, which every other table enforces with an explicit `REVOKE`.
Fixed with `REVOKE ALL ON public.analytics_events FROM anon`, matching the
pattern used by `bookings`, `profiles`, `chronicle_*` and `site_content`.

No other real defect was found. Nothing else was changed.

## 4. Security linter — accepted, by design

Seven `SECURITY DEFINER`-executable warnings remain. All four functions are
deliberate and were reviewed:

- `has_role(uuid, app_role)` — required by every RLS policy; `anon` is revoked,
  `authenticated` may only ask about role membership.
- `booked_dates`, `active_schedule_weekdays`, `active_schedule_windows` —
  the public availability channel. They return **dates and time windows only**;
  no name, e-mail, message, user id or booking id can be derived from them.
  `SECURITY DEFINER` is what lets an anonymous visitor see free slots without
  any read privilege on `bookings`.

Revoking these would break public booking availability and gain no privacy.
Accepted as designed; recorded here rather than silently ignored.

These require credentials or a signed-in session that the environment does not

- **Authenticated Admin runtime** (`/admin/*`) — no session available in this
  environment (`signed_out`); the route gate and role checks are code-verified
  only.
- **Booking end-to-end write** — requires a signed-in user; the write path is
  session-derived (`user_id` from SSR session, never from payload), schema and
  RLS now exist, but no real INSERT was executed.
- **E-mail delivery** — no `RESEND_API_KEY` / transport secret configured.
- **Telegram Admin and Statistics webhooks** — no bot tokens, webhook secrets or
  allowlists configured; both bots are correctly inert without them
  (`isBotConfigured`).
- **Analytics collection at runtime** — table exists; no live traffic recorded.
