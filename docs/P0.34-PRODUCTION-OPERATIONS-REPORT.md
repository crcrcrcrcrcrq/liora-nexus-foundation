# P0.34 — PRODUCTION OPERATIONS REPORT

## 1. Executive Summary

Etap operacyjnego domknięcia, bez przebudowy architektury. Dodano serwerową
warstwę statusu operacyjnego dla wszystkich modułów Admina, uzupełniono
szczegół rezerwacji o cenę i zabezpieczono grafik walidacją po stronie serwera.
Nie powstał żaden nowy system: status czyta te same tabele i tę samą
konfigurację, których używają istniejące moduły. Routing, Auth, RLS, model
danych, Booking, Tarot, Kronika, CMS, Theme Manager i analytics pozostały bez
zmian funkcjonalnych.

Publiczny runtime (26 tras PL/EN, 390×844) zweryfikowany realnie. Ścieżki
wymagające sesji personelu oraz transporty (e-mail, Telegram) pozostają
NOT VERIFIED — środowisko nie ma realnych sekretów, a sesji nie fabrykowano.

## 2. Inspection

Przejrzano przed implementacją: `src/routes/*`, `src/lib/*` (admin, booking,
schedule, services, blog, cms, analytics, notifications, telegram),
`src/features/*`, `src/config/routes.ts`, `src/config/i18n.ts`, warstwę sesji
(`session-middleware`, `session.server`), Telegram Admin/Stats, sitemap/robots,
`docs/supabase.md`. Duplikatów nie tworzono — status operacyjny agreguje
istniejące źródła.

## 3. Admin operations

- Nowy kontrakt stanów: `ready | configured | not_configured | unavailable | error`.
- `src/lib/ops/status.server.ts` liczy stan dla: Bookings, Services, Schedule,
  Blog, Content/CMS, Theme, Email, Telegram Admin, Telegram Statistics.
- Wejście: `fetchOperationsStatus` (sesja SSR → `requireStaffRole` → RLS).
- UI: `OperationsStatusPanel` na `/admin/integrations`.
- Brak fałszywego „Connected”: transport zawsze oznaczony jako
  NIEZWERYFIKOWANY, dopóki nie potwierdzi go realny ruch.
- Do klienta nie trafia żaden sekret ani dane osobowe — wyłącznie stany,
  liczniki i flagi boolowskie.

## 4. Booking operations

Szczegół rezerwacji pokazuje: LIORA ID, status, język, usługę, **cenę (nowe)**,
datę, godzinę, datę utworzenia, datę aktualizacji, kontakt i wiadomość klienta
wyłącznie dla roli `admin`. Akcje Confirm / Cancel / Complete korzystają
wyłącznie z `updateAdminBookingStatus`; UI renderuje tylko przejścia z
`ALLOWED_TRANSITIONS`, a serwer i tak weryfikuje `canTransition`. Dispatch
powiadomień po zmianie statusu pozostał nietknięty.

## 5. Schedule

Istniejące: walidacja zakresu, wykrywanie nakładek, unsaved/discard/save,
komunikaty błędów, wyłączanie dnia (`isActive`). **Dodano** serwerowy guard
`assertNoOverlap` w `createScheduleEntry` / `updateScheduleEntry`
(`SCHEDULE_OVERLAP`) — UI nie jest już jedynym miejscem walidacji. Model
availability i kalendarz bez zmian.

## 6. Email

`configured` / `not_configured` z `isEmailTransportConfigured()`; osobna flaga
`senderConfigured` (`STAFF_NOTIFICATION_EMAIL`). Dostarczalność: NOT VERIFIED —
nie wykonano sztucznej wysyłki.

## 7. Telegram Admin

Bez własnej logiki biznesowej: `router.server.ts` woła te same funkcje
(`listBookings`, `updateBookingStatus`, `listSchedule`, `summarize`). Rola
czytana z `user_roles` przy każdym poleceniu; `user_id`, rola i status z
payloadu nie są przyjmowane. Status: token + webhook secret + allowlista.
Handshake: NOT VERIFIED.

## 8. Telegram Statistics

Osobny token, osobny sekret, osobna allowlista, osobne źródło danych
(agregaty analytics). Zero mutacji — kanał pozostaje read-only. Status liczony
niezależnie od bota administracyjnego.

## 9. Analytics / GDPR

Przegląd bez zmian w kodzie: pseudonimowy klucz rotowany co 30 dni, brak IP,
brak fingerprintingu, allowlista metadanych (`surface`, `variant`, `spread`,
`service`, max 48 znaków), wysyłka przez idle callback, każdy błąd połknięty.
Zestaw zdarzeń pozostał ograniczony: `page_view`, CTA, booking, tarot,
language switch, legal. Nie dodano trackingu kliknięć ani żadnego pola PII.

## 10. Public runtime

Zweryfikowane realnie (Playwright, 390×844, lokalny serwer z placeholderowym
backendem — bez fabrykowania danych biznesowych): 13 tras PL i 13 EN.
Wynik: HTTP 200 na wszystkich, `html lang` zgodny z URL, `data-theme=obsidian`,
`data-template=premium-luxury`, dokładnie jeden `main`, brak horizontal
overflow, zero błędów konsoli. `h1` = 1 na wszystkich stronach dokumentowych;
`/pl/kronika`, `/pl/sanktuarium`, `/en/chronicle`, `/en/sanctuary` renderują
bramkę dostępu (stan aplikacyjny, nie dokument) — bez `h1`, zgodnie z
dotychczasowym zachowaniem. Locale nadal wynika wyłącznie z URL.

## 11. Auth/RLS

Bez zmian architektury. Nowe odczyty idą klientem sesyjnym personelu, więc
podlegają istniejącym politykom; brak uprawnień = `unavailable`. Żadnej nowej
polityki, roli ani ścieżki uprzywilejowanej.

## 21. Known limitations

- Status transportu jest deklaratywny do czasu ruchu produkcyjnego; świadomie
  nie „zazieleniamy” UI sztucznym requestem.
- Cena w szczegółach rezerwacji pochodzi z katalogu oferty, nie z kwoty
  zamrożonej w rekordzie rezerwacji (model danych nie przechowuje ceny).
- Karty `ephemeris` i `payments` pozostają oznaczone jako oczekujące na
  konfigurację — te integracje nie istnieją.
